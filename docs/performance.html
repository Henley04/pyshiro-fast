Validation

Two kinds of input, for two different questions.

Exactness and long audio: synthetic features

The scaling table above uses deterministic feature streams sampled from the model's own GMMs, with known segment boundaries. They serve two purposes: the 10-minute case can be measured at all (upstream would need about three days), and both implementations can be fed byte-for-byte identical input, so the comparison is exact rather than statistical.

DP cost depends only on the shape of the lattice, (T, N) — the loop structure and the pruning windows are derived from the state sequence, never from feature values — so the timing transfers to real audio. Feature extraction is the only extra cost there, and it is linear.

Why it is faster

The upstream kernel loops over every possible duration d for every state and frame, giving O(N·T²). The first pass — which has no duration prior, so ceil = T — is about 96 % of the runtime. Four changes remove that quadratic factor.

1. Exact pruning of the duration axis

d is only scanned where the predecessor state can actually be:

d ∈ [floor, ceil] ∩ [q − hi(src), q − lo(src)]

Cells outside that range hold -inf, so this skips work without changing the result. The second pass benefits most: with a ±60-frame window it becomes effectively O(N·window²).

2. O(1) argmax in the duration-free pass

Without a duration prior, the recurrence reduces to a sliding-window maximum:

score[n,t] = cum[t] + max_p( score[src,p] − cum[p] ),   p ∈ [t−ceil, t−floor]

The maximum over p is maintained incrementally as t advances, so each cell costs O(1) instead of O(t): O(N·T²) → O(N·T).

The value is still computed as score[src,p] + (cum[t] − cum[p]) in the original order, and ps/cum[p] are cached when the maximum is updated rather than re-read. That is why the log-likelihood is bit-identical and not merely close.

3. Compact backpointers

Upstream stores three (N, T+1) arrays. Here:

  • d (up to T) and the predecessor offset (up to 7 states) are packed into one int32: (d << 3) | offset.
  • Scores are kept only for the last K rows, where K is the longest possible skip edge (usually 1–3), in a ring buffer.

16 B per cell becomes 4 B, and the score matrix disappears.

4. Hirschberg divide-and-conquer traceback

When the packed backpointer matrix would exceed backtrace_mem_mb, the state axis is split at its midpoint, forward DP runs on the left half, reverse DP on the right half, and the best meeting frame is chosen. Both halves recurse. Memory becomes O(K·T) instead of O(N·T).

The reverse pass reuses the forward kernel: reverse the state order, reverse the time axis, flip the adjacency lists, and replace prefix sums with suffix sums. One DP implementation, not two.

Cost of the divide-and-conquer path

300 s input Time Peak RSS
full matrix (backtrace_mem_mb=4096) 45.3 s ≈ 3.4 GiB (computed)
divide-and-conquer (backtrace_mem_mb=0) 91.7 s 255 MB

The divide-and-conquer path pays log N passes, so it is 2–2.5× slower. It is chosen automatically only when the matrix would not fit in the budget. If you have RAM and want speed, raise the budget:

segments, loglik = pyshiro.forced_align_2pass(
    model, streams, state_seq, backtrace_mem_mb=4096)

Both paths return identical segments; this is checked by the test suite.

Tuning

Goal Setting
fastest on a machine with RAM backtrace_mem_mb=4096 (or higher)
lowest memory, speed irrelevant backtrace_mem_mb=0
default 1024 — full matrix up to ~250 M cells, then divide-and-conquer
long files on a small container backtrace_mem_mb=256

Rough memory for the full-matrix path: 4 · N · (T+1) bytes — about 2.3 GiB per 10 000 states at 300 s. Add ~40 MB for features and the DP context.

Reproducing these numbers

The benchmark script is in the repository:

# scaling sweep with deterministic synthetic features
python bench/bench_align_speed.py --sweep 10,20,60,120,300 \
    --model pyshiro/data/models/pyshiro-jp-v2.hsmm \
    --phonemap pyshiro/data/models/pyshiro-jp-v2_phonemap.json

# real audio through the CLI path
python bench/bench_align_speed.py --wav song.wav --lyric song.txt \
    --model pyshiro/data/models/pyshiro-jp-v2.hsmm \
    --phonemap pyshiro/data/models/pyshiro-jp-v2_phonemap.json

# one recording, with sanity statistics (and an optional reference phone timing)
python bench/real_audio_check.py --wav clip.wav \
    --phones "pau,a,k,a,i,g,u,ts,u,pau" \
    --ref-durs "0.30,0.05,0.12,0.40,0.08,0.15,0.07,0.20,0.35,0.25"

real_audio_check.py is what produced the GTSinger tables above; it takes a plain phone list, so it works with any annotated corpus.

The sweep uses features sampled deterministically from the model's own GMMs, which is what makes the exact comparison in the first section possible. Real audio adds feature extraction — linear, and well under a second for a few minutes.

What is not optimised yet

  • The kernel is memory-bound at roughly 90–130 M cells/s. A tiled sweep (time outer, states inner, blocking both) would improve cache locality and could give another 3–5×, at the cost of rewriting the inner loop.
  • The duration pass still scans a window of durations. A monotone-queue formulation exists for the Gaussian duration prior but was not implemented, because the second pass is already a small fraction of the total.
  • Feature extraction is not parallelised. For batch corpora, --jobs parallelises training only.
